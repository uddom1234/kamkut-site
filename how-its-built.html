ឯកសារ SPEC.md របស់ KamKut ចាប់ផ្តើមដោយច្បាប់មួយឃ្លា៖ កម្មវិធីកាត់តវីដេអូ offline ប៉ុណ្ណោះ គ្មានគណនី គ្មានអ៊ីនធឺណិត និងគ្មាន database សោះ (សូម្បីតែ Room, SQLite ឬ SwiftData)។ គម្រោងនីមួយៗគ្រាន់តែជាឯកសារ JSON ធម្មតានៅក្នុងទីផ្ទុកឯកជនរបស់កម្មវិធី។ ទំព័រនេះពន្យល់ពីរបៀបដែលច្បាប់នោះត្រូវបានអនុវត្តជាក់ស្តែងក្នុងកូដ ហើយមិនមែនគ្រាន់តែសរសេរក្នុងគោលការណ៍ឯកជនភាពនោះទេ។

The first thing SPEC.md says about KamKut is a rule: offline-only, no accounts, no network, no database (not even Room, SQLite or SwiftData). A project is a plain JSON file in the app's private storage. This page is about how that rule is enforced in the code, rather than only stated in a privacy policy.

Android៖ ប្រព័ន្ធប្រតិបត្តិការជាអ្នកអនុវត្តច្បាប់Android: the OS enforces it

នៅក្នុង AndroidManifest.xml កម្មវិធីលុបការអនុញ្ញាតបណ្តាញចេញពី manifest ដែលត្រូវបាន merge ដោយប្រើ tools:node="remove"។ ទោះបី library ណាមួយព្យាយាមបញ្ចូល INTERNET មកក៏ដោយ លទ្ធផលចុងក្រោយនឹងមិនមានវាទេ។ ការអនុញ្ញាតតែមួយគត់ដែលកម្មវិធីសុំគឺ RECORD_AUDIO សម្រាប់ថតសំឡេងរៀបរាប់ និង WRITE_EXTERNAL_STORAGE ដែលកំណត់ត្រឹម maxSdkVersion="28" សម្រាប់ Android 9 ប៉ុណ្ណោះ។

In AndroidManifest.xml the app strips the network permissions from the merged manifest with tools:node="remove". Even if a library tries to merge INTERNET in, the final manifest will not contain it. The only permissions the app asks for are RECORD_AUDIO (voiceovers) and WRITE_EXTERNAL_STORAGE capped at maxSdkVersion="28", which only matters on Android 9.

វិន័យដូចគ្នានេះអនុវត្តលើ dependency ផងដែរ។ ការកាត់ផ្ទៃខាងក្រោយប្រើ ML Kit Selfie Segmentation ដែល model ត្រូវបានបង្កប់ក្នុងកម្មវិធី (com.google.mlkit:segmentation-selfie:16.0.0-beta6) ហើយ meta-data ទទេ com.google.mlkit.vision.DEPENDENCIES មានន័យថា គ្មានសេវាទាញយក model ណាត្រូវបានចុះឈ្មោះទេ។ បញ្ជី dependency ក្នុង build.gradle.kts មានតែ Media3, Compose/AndroidX, kotlinx (serialization, coroutines) និង ML Kit segmentation ប៉ុណ្ណោះ គ្មានអ្វីផ្សេងទៀតទេ។

The same discipline covers dependencies. Background removal uses the ML Kit Selfie Segmentation model bundled inside the app (com.google.mlkit:segmentation-selfie:16.0.0-beta6), and the empty com.google.mlkit.vision.DEPENDENCIES meta-data means no model-download service is registered. The dependency list in build.gradle.kts is Media3, Compose and AndroidX, kotlinx (serialization, coroutines) and ML Kit segmentation, and nothing else.

iOS៖ ដោយការរចនា និងការត្រួតពិនិត្យiOS: by construction and by audit

iOS មិនមានកុងតាក់ដូច manifest ទេ ដូច្នេះការធានាមកពីអ្វីដែលកម្មវិធីភ្ជាប់ជាមួយ។ ឯកសារ project.pbxproj មិនមាន Swift package ណាមួយទេ (ចំនួនយោង package ស្មើសូន្យ) ហើយ source ទាំងអស់ក្នុង ios/Kamkut/ មិនប្រើ URLSession, URLRequest, NWConnection ឬ WKWebView សោះ។ មានតែ framework របស់ Apple ប៉ុណ្ណោះ៖ AVFoundation, Core Image, Metal, Vision, Speech និង Photos។ ឯ PrivacyInfo.xcprivacy ប្រកាស NSPrivacyTracking = false គ្មានទិន្នន័យដែលប្រមូល គ្មាន tracking domain និងប្រើតែ UserDefaults (ហេតុផល CA92.1)។

iOS has no manifest switch, so the guarantee comes from what the app links. The project.pbxproj contains no Swift packages at all (zero package references), and a search of ios/Kamkut/ finds no use of URLSession, URLRequest, NWConnection or WKWebView. Only Apple frameworks are used: AVFoundation, Core Image, Metal, Vision, Speech and Photos. PrivacyInfo.xcprivacy declares NSPrivacyTracking = false, no collected data types, no tracking domains, and a single required-reason API: UserDefaults (reason CA92.1).

កន្លែងតែមួយដែលអ៊ីនធឺណិតអាចលួចចូលបានគឺ speech។ ការបង្កើត captions ស្វ័យប្រវត្តិប្រើ SFSpeechRecognizer ជាមួយ requiresOnDeviceRecognition = true ហើយបើឧបករណ៍មិនអាចធ្វើបាន កម្មវិធីបង្ហាញសារ ជាជាងធ្លាក់ទៅប្រើបណ្តាញ (អត្ថបទកំហុសសរសេរត្រង់ៗថា "KamKut never uses the network for this")។ ភាសាខ្មែរត្រូវបានបង្ហាញជាជម្រើសដែលបិទ ពេលឧបករណ៍គ្មាន recogniser ខ្មែរសម្រាប់ដំណើរការ offline។

The one place where a network could creep in is speech. Auto captions use SFSpeechRecognizer with requiresOnDeviceRecognition = true, and if the device cannot do it the app shows a message instead of falling back to the network (the error text literally says "KamKut never uses the network for this"). Khmer is listed as a disabled option when the device has no offline Khmer recogniser.

និយាយឱ្យច្បាស់៖ លើ Android ការធានានេះកើតពីប្រព័ន្ធប្រតិបត្តិការផ្ទាល់ (វារារាំងបណ្តាញ) ចំណែកលើ iOS វាកើតពីការរចនា រួមជាមួយការត្រួតពិនិត្យ source (គ្មាន API បណ្តាញក្នុងកូដ)។ មានតែតំណពីរប៉ុណ្ណោះដែលបើក browser របស់ប្រព័ន្ធ គឺ "Sponsored by kamsophy.com" និង "Get more fonts"។ កម្មវិធីខ្លួនឯងមិនផ្ញើសំណើអ្វីសោះ។

Being precise: on Android the guarantee is mechanical (the OS blocks it); on iOS it is design plus an audit of the source (no networking API in the code). Exactly two links open the system browser, "Sponsored by kamsophy.com" and "Get more fonts". The app itself sends no request.

ការរក្សាទុកដោយឯកសារតែប៉ុណ្ណោះPersistence is just files

គ្រប់យ៉ាងរស់នៅក្នុងថតមួយក្នុងទីផ្ទុកឯកជន៖ projects/<projectId>/project.json, ថត media/ (clip ដែលនាំចូល ភ្លេង សំឡេងរៀបរាប់ និងឯកសារ cutout) និង thumb.jpg ជាជម្រើស។ លើ iOS ថតនោះនៅក្នុង Application Support/projects/ ហើយលើ Android នៅក្នុង files/projects/។ ការកំណត់ដូចជា appearance និងជម្រើស export ត្រូវបានរក្សាក្នុង UserDefaults / SharedPreferences ។ font ដែលអ្នកប្រើនាំចូលរស់នៅក្នុងថត fonts/ កម្រិតកម្មវិធី មិនមែនក្នុងគម្រោងនីមួយៗទេ។ ការ export (ទៅ Photos, ទៅ MediaStore ឬតាម share sheet របស់ iOS) គឺជាផ្លូវដែលទិន្នន័យចេញពីទីផ្ទុកឯកជន ហើយវាតែងតែជាសកម្មភាពរបស់អ្នកប្រើ។

Everything lives in one folder tree in private storage: projects/<projectId>/project.json, a media/ folder (imported clips, music, voiceovers, cutouts) and an optional thumb.jpg. On iOS that tree is under Application Support/projects/; on Android under files/projects/. Settings such as appearance and export options live in UserDefaults / SharedPreferences. Fonts the user imports live in an app-wide fonts/ folder, not per project. Exporting (to Photos, to MediaStore, or through the iOS share sheet) is how data leaves private storage, and it is always a user action.

កម្មវិធី native ពីរ ស្រទាប់ដូចគ្នាTwo native apps, the same layers #

KamKut មិនមែនជា shell តែមួយដែលដំណើរការលើគ្រប់ប្រព័ន្ធទេ។ វាជាកូដពីរដាច់ដោយឡែក៖ Swift + SwiftUI លើ iOS និង Kotlin + Jetpack Compose លើ Android។ អ្វីដែលចែករំលែកមានតែ SPEC.md ដែលជាកិច្ចសន្យា (spec សរសេរថាមុខងារលើកម្មវិធីទាំងពីរ "MUST implement identically") និងទ្រង់ទ្រាយ project.json។ តម្លៃនៃជម្រើសនេះគឺរាល់មុខងារត្រូវសរសេរពីរដង ប៉ុន្តែអត្ថប្រយោជន៍គឺអាចប្រើ AVFoundation, Core Image និង Metal បានពេញលេញនៅម្ខាង ហើយ Media3 ជាមួយ GLSL នៅម្ខាងទៀត។

KamKut is not one cross-platform shell. It is two separate codebases: Swift and SwiftUI on iOS, Kotlin and Jetpack Compose on Android. The only things they share are SPEC.md, the contract (the spec says features on both platforms "MUST implement identically"), and the project.json format. The cost is that every feature is written twice. The payoff is full access to AVFoundation, Core Image and Metal on one side, and Media3 with GLSL on the other.

កម្មវិធីទាំងពីរមានស្រទាប់ទាំងប្រាំដូចគ្នា។ ពីក្រោមឡើងលើ៖

Both apps have the same five layers. From the bottom up:

  1. Model៖ ប្រភេទតម្លៃសុទ្ធ។ iOS: Model/Project.swift (struct ជា Codable)។ Android: data/Models.kt (data class ជា @Serializable)Model: pure value types. iOS: Model/Project.swift (Codable structs). Android: data/Models.kt (@Serializable data classes).
  2. Store៖ អាន/សរសេរ project.json។ iOS: ProjectStore។ Android: ProjectStoreStore: reads and writes project.json. iOS: ProjectStore. Android: ProjectStore.
  3. Editor state៖ គម្រោងដែលកំពុងបើក + undo + autosave។ iOS: EditorModel (@MainActor ObservableObject)។ Android: EditorViewModel (StateFlow<Project>)Editor state: the open project plus undo and autosave. iOS: EditorModel (@MainActor ObservableObject). Android: EditorViewModel (StateFlow<Project>).
  4. Render engine៖ បម្លែង Project ទៅជា composition។ iOS: CompositionBuilder + LayerCompositor។ Android: CompositionBuilder + ClipShader + TransitionRendererRender engine: turns a Project into a composition. iOS: CompositionBuilder + LayerCompositor. ការអត់ឱនចំពោះ key មិនស្គាល់ និងតម្លៃមិនត្រឹមត្រូវTolerating unknown keys and bad values

spec សរសេរថា "Unknown keys must be ignored when decoding"។ Android ធ្វើវាតាមរយៈ configuration នៃ Json៖ ignoreUnknownKeys និង coerceInputValues។ iOS ធ្វើលើសពីនេះបន្តិច៖ Codable មិនអើពើ key ដែលមិនស្គាល់ដោយធម្មជាតិ ហើយ initializer ដែលសរសេរដោយដៃប្រើ helper value(_:_:) ដែលសង់លើ try? ដូច្នេះប្រភេទខុស ឬ key បាត់ នឹងធ្លាក់ទៅតម្លៃលំនាំដើម ជាជាងធ្វើឱ្យគម្រោងទាំងមូលបើកមិនកើត។

The spec says "Unknown keys must be ignored when decoding". Android does it through the Json configuration: ignoreUnknownKeys and coerceInputValues. iOS goes a step further: Codable ignores unknown keys by nature, and the hand-written initialisers use a value(_:_:) helper built on try?, so a wrong type or a missing key falls back to the default instead of making the whole project unreadable.

iOS ក៏សម្អាតតម្លៃពេល decode ដែរ៖ trimEndMs ដែលខុសត្រូវបានកំណត់ទៅ durationMs, speed <= 0 ត្រូវក្លាយជា 1 ហើយ transition id ត្រូវបាន canonicalize ពេលផ្ទុក។ key បន្ថែមដែលមានតែលើ iOS (ឧ. revFileName លើ clip, sourceClipID និង bakedSpeed លើ audio) ត្រូវបានចំណាំក្នុងកូដថា Android មិនអើពើ ដែលដំណើរការបានដោយសារការអត់ឱនទាំងសងខាង។

iOS also sanitises values while decoding: a bad trimEndMs is reset to durationMs, speed <= 0 becomes 1, and transition ids are canonicalised on load. iOS-only extra keys (for example revFileName on clips and sourceClipID / bakedSpeed on audio items) are marked in the code as ignored by Android, which only works because of the tolerance on both sides.

Media ត្រូវបាន copy ចូលគម្រោងMedia is copied into the project

នៅពេលនាំចូល ឯកសារត្រូវបាន copy (ឬ move ពី temp ក្នុងករណី PhotosPicker លើ iOS) ចូលថត media/ របស់គម្រោង។ ដូច្នេះគម្រោងនៅតែបើកបាន ទោះបីរូបភាព ឬវីដេអូដើមត្រូវបានលុបចេញពី gallery ។ iOS ដាក់ឈ្មោះ <prefix>_<8 តួ hex>.<ext> ឯ Android ដាក់ឈ្មោះ <prefix>_<millis>.<ext>។ រូបភាព layer លើ Android ត្រូវបាន decode តាម EXIF បន្ថយទំហំអតិបរមា 2048 px រួចរក្សាជា PNG ដើម្បីឱ្យវាត្រង់ជានិច្ច។ ពេលលុប clip លើ iOS ឯកសារ media ត្រូវបានលុបតែនៅពេលគ្មានអ្វីយោងវាទៀត។ ការអូសចេញដើម្បីលុបរក្សាឯកសារទុក ដើម្បីឱ្យ Undo ស្តារបាន។

On import the file is copied (or moved from a temp location, in the case of PhotosPicker on iOS) into the project's media/ folder. That is why a project still opens when the original photo or video is gone from the gallery. iOS names files <prefix>_<8 hex chars>.<ext>, Android names them <prefix>_<millis>.<ext>. Android decodes layer images with EXIF orientation, caps them at 2048 px and stores them as PNG so they are always upright. On iOS, deleting a clip only removes its media file once nothing references it; drag-to-delete keeps the files so that Undo can restore the clip.

Autosave និង undoAutosave and undo

រាល់ពេល project ផ្លាស់ប្តូរ លើ iOS didSet កត់ត្រា snapshot ចាស់ចូល EditorHistory សម្រេចថាត្រូវ rebuild composition ឬគ្រាន់តែ update parameter រស់ៗ រួចកំណត់ពេលរក្សាទុក 600 ms ក្រោយ (debounce)។ ការសរសេរប្រើ .atomic ។ លើ Android រាល់ edit រក្សាទុកភ្លាមៗលើ Dispatchers.IO (បោះបង់ការរក្សាទុកមុនដែលនៅមិនទាន់ចប់) ដោយសរសេរទៅ project.json.tmp រួចប្តូរឈ្មោះ ដូច្នេះការគាំងកណ្តាលការរក្សាទុកមិនធ្វើឱ្យគម្រោងខូចទេ ហើយ onCleared រក្សាទុកម្តងទៀតជាចុងក្រោយ។

Whenever project changes on iOS, didSet records the old snapshot in EditorHistory, decides whether the composition must be rebuilt or only live parameters updated, and then schedules a save 600 ms later (a debounce). The write uses .atomic. On Android every edit saves immediately on Dispatchers.IO (cancelling any save still in flight), writing to project.json.tmp and renaming it, so a crash mid-save never corrupts a project; onCleared saves once more at the end.

Undo គឺជា snapshot នៃ Project ទាំងមូល។ ព្រោះ Project ជាតម្លៃ ដូច្នេះការ undo គ្រាន់តែដាក់ Project ចាស់ត្រឡប់មកវិញ ហើយ media ដែលមានទំហំធំមិនត្រូវបាន copy ទេ ព្រោះ snapshot មានតែ model ប៉ុណ្ណោះ។ លើ iOS ការកែប្រែលឿនៗជាប់គ្នា (ដូចអូស slider) បញ្ចូលគ្នាក្នុងជំហានតែមួយ (ក្នុងរយៈ 0.8 វិនាទី) ហើយ begin()/end() ដាក់ក្រុមការសរសេរច្រើនជាជំហានតែមួយ (ដូចអូស trim handle)។ លើ Android កាយវិការប្រើ liveEdit ហើយ endLive កត់ត្រាជំហាន undo តែមួយ។

Undo is a snapshot of the whole Project. Since Project is a value, undoing just puts an older Project back, and the heavy media files are never copied because a snapshot holds only the model. On iOS, rapid consecutive edits (dragging a slider) coalesce into one step within 0.8 s, and begin() / end() group several writes into a single step (a trim-handle drag). On Android gestures use liveEdit and endLive records exactly one undo step.

Timeline៖ គណិតវិទ្យា និងកាយវិការបែប CapCutThe timeline: math and CapCut-style gestures #

ប្រវែង timelineTimeline length

នៅ v1 ប្រវែង timeline គឺ Σ (trimEndMs − trimStartMs) / speed។ នៅ v3 transition បែប overlap ធ្វើឱ្យ clip B ចាប់ផ្តើមមុនពេល A ចប់ ដូច្នេះរូបមន្តក្លាយជា Σ ប្រវែង clip − Σ d ដោយ d ជា overlap របស់ transition នីមួយៗ៖

In v1 the timeline length is Σ (trimEndMs − trimStartMs) / speed. In v3 overlap transitions make clip B start before A ends, so the formula becomes Σ clip durations − Σ d, where d is the overlap of each transition:

  • ប្រវែងលើ timeline របស់ clip = (trimEnd − trimStart) / clamp(speed, 0.1, 10)។ រូបថត និង freeze frame មិនអើពើ speed នៅលើ iOS (ប្រវែងអប្បបរមា 100 ms)A clip's timeline duration is (trimEnd − trimStart) / clamp(speed, 0.1, 10). On iOS photos and freeze frames ignore speed (minimum 100 ms).
  • d = min(clamp(transitionMs, 100, 1500), dur(A)/2, dur(B)/2) ហើយ d = 0 ពេល transition ជា none ឬជា clip ចុងក្រោយ។ Android ក៏កំណត់ d ទៅ 0 ផងដែរ ប្រសិនបើវាតិចជាង 50 msd = min(clamp(transitionMs, 100, 1500), dur(A)/2, dur(B)/2), and d = 0 for none or for the last clip. Android additionally treats d below 50 ms as 0.
  • clip i+1 ចាប់ផ្តើមនៅ end(i) − d(i)Clip i+1 starts at end(i) − d(i).
  • overlay, layer, effect និង audio រក្សាម៉ោងដាច់ខាត (absolute) ដូច្នេះវាមិនរំកិលពេលអ្នកប្តូរ transition។ clampedToTimeline() កាត់អ្វីដែលហួសចុង timelineOverlays, layers, effects and audio keep absolute times, so they do not shift when you change a transition. clampedToTimeline() trims anything that runs past the end.

ឧទាហរណ៍គណនា (លេខគំរូ ដើម្បីបង្ហាញរូបមន្ត មិនមែនលទ្ធផលវាស់វែងទេ)៖ clip A = 4000 ms, B = 2000 ms, C = 3000 ms។ A→B មាន dissolve 500 ms ហើយ B→C ស្នើ 1500 ms។ d₁ = min(500, 2000, 1000) = 500។ d₂ = min(1500, 1000, 1500) = 1000 ព្រោះត្រូវបានកំណត់ត្រឹមពាក់កណ្តាលនៃ B។ ប្រវែងសរុប = 9000 − 1500 = 7500 ms ហើយ clip ចាប់ផ្តើមនៅ 0, 3500 និង 4500 ms។

A worked example (made-up numbers to show the formula, not a measurement): clips A=4000 ms, B=2000 ms, C=3000 ms. A→B has a 500 ms dissolve and B→C asks for 1500 ms. d₁ = min(500, 2000, 1000) = 500. d₂ = min(1500, 1000, 1500) = 1000, capped by half of B. Length = 9000 − 1500 = 7500 ms, and the clips start at 0, 3500 and 4500 ms.

Trim, split, merge និង speedTrim, split, merge and speed

Trim។ ការអូស handle ផ្លាស់ប្តូរ trimStartMs ឬ trimEndMs ជាបន្តបន្ទាប់។ ចម្ងាយដែលអូសលើ timeline (ms) គុណនឹង speed ក្លាយជាចម្ងាយក្នុង source (ព្រោះ clip ដែលលឿន 2× ប្រើ source ច្រើនជាងក្នុងរយៈពេលដូចគ្នា)។ ប្រវែងអប្បបរមាគឺ 200 ms (minClipMs / MIN_CLIP_MS) ហើយ playhead ដើរតាមគែមដែលកំពុងអូស។ គ្រប់ការអូសទាំងមូលជាជំហាន undo តែមួយ។

Trim. Dragging a handle changes trimStartMs or trimEndMs continuously. The drag distance on the timeline (ms) is multiplied by the speed to get the distance in the source (a 2× clip consumes more source in the same time). The minimum length is 200 ms (minClipMs / MIN_CLIP_MS), the playhead follows the edge being dragged, and the whole drag is one undo step.

Split។ កន្លែងដាច់ត្រូវបានគណនាពីទីតាំង playhead៖ local = trimStart + (t − clipStart) × speed ហើយទាំងសងខាងត្រូវមានយ៉ាងហោចណាស់ 100 ms បើមិនដូច្នេះទេ កម្មវិធីបង្ហាញសារ។ ពេល clip ពីរត្រួតគ្នាក្នុង transition clip ចូល (incoming) គឺជាអ្នកដែលត្រូវបំបែក។ លើ iOS clip ទីមួយបាត់ transition ចេញ (វាទៅជាកម្មសិទ្ធិរបស់ផ្នែកទីពីរ)។ លើ Android ការគណនារក្សា trim ក្នុងកូអរដោនេ source ដើម ដូច្នេះប្រសិនបើ clip ត្រូវបាន reverse វាគណនាពីចុងវិញ។

Split. The cut point comes from the playhead: local = trimStart + (t − clipStart) × speed, and both halves must keep at least 100 ms or the app shows a message instead. When two clips overlap in a transition, the incoming clip is the one that is split. On iOS the first half loses its outgoing transition (it stays with the second half). On Android trims stay in the original source's coordinates, so for a reversed clip the cut is computed from the end.

Merge។ កម្មវិធីបញ្ចូល clip ទីមួយ និងទីពីរចូលគ្នាតែនៅពេលវាជាបំណែកជាប់គ្នានៃ source តែមួយ (ក្រោយ split) និង speed ដូចគ្នា។ iOS អនុញ្ញាតគម្លាតមិនលើស 50 ms ហើយ Android ទាមទារឱ្យចំណុចស្មើគ្នាពិតប្រាកដ។ បើមិនដូច្នេះទេ ផ្នែកទាំងពីរត្រូវបានបញ្ចូលគ្នាដោយស្វ័យប្រវត្តិពេល export ព្រោះ clip ទាំងអស់ concatenate ជានិច្ច។

Merge. The app joins a clip with the next one only when they are contiguous pieces of the same source (as after a split) with the same speed. iOS allows a gap of up to 50 ms, Android requires the points to be exactly equal. Otherwise the clips are simply joined at export, because all clips always concatenate.

Speed។ ជួរគឺ 0.1×–10× (spec v1 មានតែ 0.5/1/1.5/2 ហើយ v3 បានពង្រីក)។ លើ iOS speed ត្រូវបានអនុវត្តដោយ scaleTimeRange លើទាំងវីដេអូ និងសំឡេង ហើយ audioTimePitchAlgorithm = .spectral រក្សា pitch ក្នុង preview។ លើ Android វាជា SpeedProvider ថេរលើ EditedMediaItem។

Speed. The range is 0.1×–10× (the v1 spec's 0.5/1/1.5/2 was widened in v3). On iOS speed is applied with scaleTimeRange on both the video and the audio track, and audioTimePitchAlgorithm = .spectral keeps pitch in the preview. On Android it is a constant SpeedProvider on the EditedMediaItem.

កាយវិការ៖ handle, ចុចយូរ, អូសចេញGestures: handles, long-press, drag out

spec កំណត់ពីរកាយវិការ។ ទី១ clip ដែលបានជ្រើសបង្ហាញ trim handle ពណ៌មាសទទឹង ~14 នៅគែមឆ្វេង និងស្តាំ។ ទី២ ចុចយូរ ~0.35 វិនាទីដើម្បីលើក clip (ពង្រីក 1.05 + haptic) អូសឆ្វេង/ស្តាំដើម្បីតម្រៀប ហើយអូសឡើងលើហួសចម្ងាយកំណត់ ហើយលែងដើម្បីលុប (មានសារ undo)។

The spec defines two gestures. First, a selected clip shows gold trim handles about 14 wide on its left and right edges. Second, long-press for about 0.35 s to pick a clip up (scale 1.05 plus a haptic), drag left or right to reorder, and drag it up past a threshold and release to delete it (with an undo toast).

iOS។ Handle មានតំបន់ប៉ះទទឹង 26 pt ប៉ុន្តែមានតែបន្ទះនៅគែមប៉ុណ្ណោះដែលទទួលការប៉ះ ដូច្នេះការចុចលើតួ bar នៅតែជ្រើស clip ហើយ ScrollView ខាងក្រៅនៅតែ scroll បាន។ ការចុចយូរគឺ LongPressGesture(minimumDuration: 0.35, maximumDistance: 12) ដែល .sequenced(before: DragGesture) ដូច្នេះការអូសចាប់ផ្តើមតែក្រោយពេលចុចយូរជោគជ័យ ហើយមិនជាន់ការ scroll ឡើយ។ ការអូសឡើងលើ 50 pt ឬច្រើនជាងនេះ រួចលែង នឹងហៅ removeClipByDrag ដែលបង្ហាញ toast "Clip removed" ជាមួយប៊ូតុង Undo រយៈពេល 5 វិនាទី។

iOS. A handle is a 26 pt wide hit area, but only that strip at the edge is hit-testable, so tapping the bar body still selects the clip and the surrounding ScrollView still scrolls. The long-press is a LongPressGesture(minimumDuration: 0.35, maximumDistance: 12) .sequenced(before: DragGesture), so the drag only begins after the long-press succeeds and never fights scrolling. Dragging 50 pt or more upward and releasing calls removeClipByDrag, which shows a "Clip removed" toast with Undo for 5 seconds.

Android។ ការចុចយូរប្រើ detectDragGesturesAfterLongPress ដែលទុកឱ្យ parent scroll ដោយសេរី រហូតដល់ការចុចយូរកើតឡើង។ Handle មានតំបន់ប៉ះទទឹង 28 dp (មើលឃើញ 14 dp) ដែលលាតចេញក្រៅបន្តិច ដើម្បីងាយចាប់។ ការអូសលុបប្រើ DELETE_DRAG_DP = 60.dp ហើយ trim ក៏ប្រើ liveEdit / endLive ដែរ។ មានភាពខុសគ្នាតូចមួយ៖ spec សរសេរ 60 ប៉ុន្តែ iOS ប្រើ 50 pt។

Android. The long-press uses detectDragGesturesAfterLongPress, which leaves the parent's scrolling alone until the long-press fires. Handles have a 28 dp touch area (14 dp visible) that extends slightly outward so they are easy to grab. Drag-to-delete uses DELETE_DRAG_DP = 60.dp, and trims go through liveEdit / endLive too. One small discrepancy: the spec says 60, while iOS uses 50 pt.

លើ iOS ការផ្គូផ្គងពេលវេលា↔ទីតាំង x ស្ថិតក្នុង TimelineMap ដែលជាលីនេអ៊ែរ (x = វិនាទី × pxPerSecond) ក្នុង v3 ព្រោះ clip ត្រួតគ្នាក្នុងពេលវេលា ដូច្នេះ track ទាំងអស់ (layer, text, audio, effect) ប្រើមាត្រដ្ឋានតែមួយ។ លើ Android timeline អាចពង្រីកដោយ pinchZoom ដែលឆ្លើយតបតែពេលមានពីរម្រាមដៃប៉ុណ្ណោះ។

On iOS the time↔x mapping lives in TimelineMap, which is linear (x = seconds × pxPerSecond) in v3 because clips overlap in time, so every track (layers, text, audio, effects) shares one scale. On Android the timeline zooms with pinchZoom, a modifier that only reacts when two fingers are down.

Pipeline render លើ iOSThe rendering pipeline on iOS #

គំនិតកណ្តាលលើ iOS គឺ CompositionBuilder.build បម្លែង Project ទៅជា AVMutableComposition រួចភ្ជាប់ AVVideoComposition ដែលប្រើ compositor ផ្ទាល់ខ្លួន។ README ដើមរបស់ iOS ពណ៌នាអំពី handler របស់ Core Image ប៉ុន្តែកូដបច្ចុប្បន្នបានលើសពីនោះ៖ ឥឡូវនេះរាល់ frame ត្រូវបាន render ដោយ class AVVideoCompositing មួយ ដែល preview និង export ប្រើរួមគ្នា។

The central idea on iOS: CompositionBuilder.build turns a Project into an AVMutableComposition and attaches an AVVideoComposition that uses a custom compositor. The original iOS README describes a Core Image handler, but the code has since grown past that: every frame is now rendered by one AVVideoCompositing class, shared by the preview and the exporter.

  1. Clip មេឆ្លាស់គ្នារវាង track វីដេអូពីរ (A/B, k = i % 2) និង track សំឡេងពីរ ដើម្បីអាន clip ពីរក្នុងពេលតែមួយក្នុង transitionMain clips alternate between two video tracks (A/B, k = i % 2) and two audio tracks, so two clips can be read at the same time during a transition.
  2. Speed = scaleTimeRange។ រូបថត និង freeze frame ប្រើវីដេអូខ្មៅ 1 វិនាទី (160×90, cache) ដែលត្រូវលាតសន្ធឹងទៅប្រវែង clip ដើម្បីផ្តល់ពេលវេលា ហើយ pixel មកពី CIImageSpeed is scaleTimeRange. Photos and freeze frames use a cached 1-second black video (160×90) stretched to the clip's length as a timing source; the pixels come from a CIImage.
  3. Reverse ត្រូវបាន render ជាមុនទៅ media/rev_<clipId>.mp4 (ReverseRenderer) ហើយ trim ត្រូវបានបកប្រែទៅកូអរដោនេរបស់ឯកសារដែលលេងReverse is pre-rendered to media/rev_<clipId>.mp4 (ReverseRenderer) and the trims are re-expressed in the played file's coordinates.
  4. វាបង្កើត KamkutInstruction មួយសម្រាប់ time slice នីមួយៗ៖ clip តែមួយ ឬ overlap រវាង clip ពីរជាមួយ transition id + progressIt creates one KamkutInstruction per time slice: a single clip, or an overlap of two clips with a transition id and progress.
  5. LayerCompositor (AVVideoCompositing) render frame នីមួយៗតាមរយៈ FramePipeline៖ clip → transition → effects → layers → overlays (export)LayerCompositor (AVVideoCompositing) renders each frame through FramePipeline: clip, transition, effects, layers, then overlays (on export).
  6. លទ្ធផលជា BGRA CVPixelBuffer តាមរយៈ CIContext ក្នុង sRGBThe result goes out as a BGRA CVPixelBuffer via a CIContext in sRGB.

Frame មួយរបស់ clipOne clip frame

ClipRenderer.render បង្កើត frame ទំហំស្មើ canvas ដែលមិនថ្លា (opaque) តាមលំដាប់៖ source → crop → rotate/flip → fit ឬ fill → look (filter/adjust) → scale/offset/keyframes → ដាក់លើផ្ទៃខាងក្រោយ។ ផ្ទៃខាងក្រោយអាចជាពណ៌ខ្មៅ ពណ៌ណាមួយ រូបភាព ឬ blur (យក clip ខ្លួនឯង fill ពេញ canvas រួច Gaussian blur កាំប្រហែល 6% នៃទទឹង canvas គណនានៅទំហំមួយភាគបួន ហើយធ្វើឱ្យងងឹតបន្តិច)។ ពេល clip fill ពេញ canvas ដោយគ្មាន transform ការគូរផ្ទៃខាងក្រោយត្រូវបានរំលង។

ClipRenderer.render builds a canvas-sized, opaque frame in this order: source, crop, rotate/flip, fit or fill, look (filter and adjust), scale / offset / keyframes, then over the background. The background is black, a colour, an image, or blur (the clip itself filled to the canvas, then Gaussian-blurred with a radius of about 6% of the canvas width, computed at quarter size and slightly darkened). When a clip fills the whole canvas untransformed, drawing the background is skipped.

Metal CIKernel ផ្ទាល់ខ្លួនCustom Metal CIKernels

Filter ពណ៌ភាគច្រើនប្រើ Core Image ស្តង់ដារ (CIPhotoEffectMono, CISepiaTone, CIVibrance …)។ ប៉ុន្តែ Vignette និង VHS គឺជា kernel របស់ Metal ដែលសរសេរជា Metal Shading Language ហើយ compile នៅពេលដំណើរការជាមួយ CIKernel.kernels(withMetalString:) ពី string ក្នុង Filters.swift (មិនមែនឯកសារ .metal ក្នុង bundle ទេ)។ ពួកវាជា kernel ប្រភេទ [[stitchable]]។

Most colour looks use stock Core Image filters (CIPhotoEffectMono, CISepiaTone, CIVibrance and so on). Vignette and VHS, however, are Metal kernels written in the Metal Shading Language and compiled at run time with CIKernel.kernels(withMetalString:) from a string inside Filters.swift (not a .metal file in the bundle). They are [[stitchable]] kernels.

kernel ត្រូវបានជ្រើសម្តងគត់នៅពេលចាប់ផ្តើម។ នៅលើ Simulator, នៅលើឧបករណ៍ដែល Metal មិនគាំទ្រ dynamic library, ឬបើការ compile បរាជ័យ កម្មវិធីប្រើច្រវាក់ filter របស់ Core Image ដែលស្មើគ្នាជំនួស (gradient រង្វង់គុណនឹងរូបភាព សម្រាប់ vignette និង CIColorMatrix + CIStripesGenerator + CIRandomGenerator សម្រាប់ VHS)។ កូដកត់ហេតុផលទុកថា Simulator "accepts the source but renders a pass-through" (ទទួលកូដ ប៉ុន្តែ render ដោយមិនប្តូរអ្វីសោះ)។

The kernels are chosen once at startup. On the Simulator, on a device whose Metal lacks dynamic-library support, or if compilation fails, the app uses equivalent stock Core Image chains (a radial-gradient multiply for the vignette; CIColorMatrix plus CIStripesGenerator plus CIRandomGenerator for VHS). The code records the reason: the Simulator "accepts the source but renders a pass-through".

ការកែសម្រួលពណ៌ (adjust) ក៏ជាច្រវាក់ Core Image ដែរ៖ exposure, highlights/shadows, temperature/tint, hue, fade, sharpen, vignette និង grain (noise ចៃដន្យ soft-light blend ផ្លាស់ប្តូរមួយ frame ម្តង)។ filterIntensity លាយ frame ដែលបាន filter ពីលើដើមតាមអាល់ហ្វា។

Colour adjustments (adjust) are Core Image chains as well: exposure, highlights/shadows, temperature/tint, hue, fade, sharpen, vignette and grain (random noise soft-light blended, different every frame). filterIntensity mixes the filtered frame over the original by alpha.

TransitionTransitions

មាន transition ពិតចំនួន 22 (បូក none)។ TransitionRenderer.apply ទទួល frame A និង B ទំហំ canvas ព្រមទាំង progress p ពី 0 ដល់ 1 ដែលត្រូវបានធ្វើឱ្យរលូនដោយ smoothstep (លើកលែង glitch និង pixelate ដែលនៅជាលីនេអ៊ែរ)។ ឧទាហរណ៍៖ slide រំកិល B ពីលើ A ដែលនៅស្ងៀម; wipe ប្រើ gradient ជា mask ជាមួយ CIBlendWithMask (feather 2%); iris ប្រើ radial gradient; wipeClock គូរ mask ជាមុំ; whipLeft/Right គឺ push បូក CIMotionBlur។ Glitch ប្រើ RNG ដែលកំណត់ seed (SeededRNG) ដូច្នេះ frame ដដែលចេញលទ្ធផលដដែលទាំងក្នុង preview និង export។

There are 22 real transitions (plus none). TransitionRenderer.apply takes the canvas-sized frames A and B and a progress p from 0 to 1, eased with smoothstep (except glitch and pixelate, which stay linear). For example: slides move B over a static A; wipes use a gradient as a mask with CIBlendWithMask (with a 2% feather); iris uses a radial gradient; wipeClock draws an angular mask; whipLeft/Right is a push plus CIMotionBlur. Glitch uses a seeded RNG (SeededRNG) so the same frame renders identically in preview and export.

transition ចាស់ fade, flash និង zoom ត្រូវបាន map ពេល decode ទៅ dissolve, dipWhite និង zoomIn ដូចដែល Transitions.canonical ធ្វើ។ ដូច្នេះគម្រោងចាស់នៅតែដំណើរការ។

The legacy ids fade, flash and zoom are mapped on decode to dissolve, dipWhite and zoomIn by Transitions.canonical, so old projects keep working.

Effects, layers (PiP) និង textEffects, layers (PiP) and text

Effects។ ផ្លូវ effects មាន 16 ប្រភេទ (shake, zoomPulse, rgbSplit, glitch, blur, filmGrain, vhs, strobe, mirror, kaleido, vignettePulse, sepiaFade, invertFlash, letterbox, lightLeak, retro) ហើយត្រូវបានអនុវត្តលើ output របស់ track មេ នៅក្រោម layer និងអត្ថបទ។ Layers។ វីដេអូ layer នីមួយៗមាន composition track ផ្ទាល់ខ្លួន ឯរូបភាព layer ជា CIImage។ place() អនុវត្តតាមលំដាប់៖ chroma key → scale → mask/ជ្រុងមូល → បង្វិល/ទីតាំង → opacity ហើយ blend ដោយ blend filter របស់ Core Image ដូច្នេះ blend mode (multiply, screen, overlay, darken, lighten, add, softLight) ជា blend ពិតប្រាកដ។ Chroma key ប្រើ CIColorCube 48³ ដែលបង្កើតពីចម្ងាយ Cb/Cr ជាមួយការទប់ស្កាត់ពណ៌លេចធ្លាយ (spill)។ អត្ថបទ។ ត្រូវបានពន្យល់នៅផ្នែកក្រោយ។

Effects. The effects track has 16 kinds (shake, zoomPulse, rgbSplit, glitch, blur, filmGrain, vhs, strobe, mirror, kaleido, vignettePulse, sepiaFade, invertFlash, letterbox, lightLeak, retro) and is applied to the main track's output, under layers and text. Layers. Each video layer gets its own composition track, while image layers are CIImages. place() applies, in order: chroma key, scale, mask / rounded corners, rotation and position, opacity; layers are blended with Core Image blend filters, so the blend modes (multiply, screen, overlay, darken, lighten, add, softLight) are true blends. The chroma key is a generated 48³ CIColorCube built from Cb/Cr distance with light spill suppression. Text. Covered in its own section below.

របៀបដែល preview ស្របនឹង exportHow the preview matches the export

ទាំង preview និង export ហៅ CompositionBuilder.build ដូចគ្នា ហើយប្រើ LayerCompositor ដូចគ្នា ដូច្នេះ filter, transition, effect, layer, speed និង audio ដើរកូដតែមួយ។ ភាពខុសគ្នាមានតែបីប៉ុណ្ណោះ៖ (1) preview កសាងនៅទំហំចំហៀងខ្លី 720 ឯ export ប្រើការជ្រើសរបស់អ្នក, (2) preview មិនដាក់ overlay អត្ថបទក្នុង compositor (includeOverlays: false) ទេ ដោយ SwiftUI គូរវាដើម្បីឱ្យអូសបាន ដោយប្រើ OverlayRenderer.raster ដូចគ្នានឹង export ហើយ (3) export កំណត់ frame rate ដែលបានជ្រើស។

Both the preview and the export call the same CompositionBuilder.build and use the same LayerCompositor, so filters, transitions, effects, layers, speed and audio run the same code. There are only three differences: (1) the preview builds at a 720 short side while export uses your choice, (2) the preview leaves text overlays out of the compositor (includeOverlays: false) and SwiftUI draws them so they can be dragged, using the very same OverlayRenderer.raster that export uses, and (3) export sets the chosen frame rate.

ដើម្បីឱ្យការកែប្រែមានអារម្មណ៍រហ័ស មិនមែនគ្រប់ការកែប្រែទាំងអស់ទាមទារ rebuild ទេ។ v3NeedsRebuild ឆ្លើយ "បាទ" សម្រាប់ audio, aspect ratio, ឬរចនាសម្ព័ន្ធ clip/layer (rebuild ត្រូវបាន debounce 0.25 វិនាទី)។ ការផ្លាស់ប្តូរ filter, transform, effect និងផ្ទៃខាងក្រោយ (v3LiveChanged) ត្រូវបានរុញចូល RenderContext ដែលការពារដោយ NSLock ដូច្នេះ frame បន្ទាប់ប្រើតម្លៃថ្មី ដោយមិនបង្កើត composition ឡើងវិញ។ ការបោះបង់សំណើ render ដែលហួសសម័យប្រើ "generation counter" ក្នុង compositor។

To keep edits feeling instant, not every edit needs a rebuild. v3NeedsRebuild answers yes for audio, aspect ratio, or clip/layer structure (rebuilds are debounced by 0.25 s). Changes to looks, transforms, effects and the background (v3LiveChanged) are pushed into a RenderContext guarded by an NSLock, so the next frame uses the new values without building a new composition. Stale render requests are cancelled with a generation counter in the compositor.

Pipeline render លើ AndroidThe rendering pipeline on Android #

Android ប្រើគំរូខុសគ្នា។ CompositionBuilder.build បម្លែង Project ទៅជា Composition របស់ Media3 (សំណុំនៃ EditedMediaItemSequence)។ item នីមួយៗមាន Effects(audio processors, video effects) ហើយទាំង Transformer (export) និង CompositionPlayer (preview) អាន composition តែមួយនោះ។ ការងាររូបភាពភាគច្រើនគឺ GLSL។

Android uses a different model. CompositionBuilder.build turns a Project into a Media3 Composition (a set of EditedMediaItemSequences). Each item carries Effects(audio processors, video effects), and both the Media3 Transformer (export) and CompositionPlayer (preview) read that same composition. Most of the visual work is GLSL.

  1. Track មេគឺ sequence តែមួយ។ clip នីមួយៗក្លាយជា EditedMediaItem ដែលមាន clipping (trim) និងល្បឿន (SpeedProvider ថេរ)The main track is one sequence. Each clip becomes an EditedMediaItem with clipping (the trim) and a speed (a constant SpeedProvider).
  2. video effects ក្នុង item = ClipShader ជា GLSL pass តែមួយ (crop → rotate → flip → fit/fill → scale/offset/keyframes → ផ្ទៃខាងក្រោយ → filter → brightness/contrast/saturation → adjust) បន្ទាប់មក lane នៃ effects trackThe item's video effects are ClipShader, a single GLSL pass (crop, rotate, flip, fit/fill, scale/offset/keyframes, background, filter, brightness/contrast/saturation, adjust), followed by the lanes of the effects track.
  3. Transition overlap ត្រូវបាន render ជាមុនម្តងក្នុងមួយចំណុចកាត់ទៅជា MP4 តូចមួយ ("T segment") ហើយ sequence លេង A-body, T, B-bodyEach overlap transition is pre-rendered once per cut into a small cached MP4 (a "T segment"), and the sequence plays A-body, T, B-body.
  4. ភ្លេង សំឡេងរៀបរាប់ sfx និង tts នីមួយៗមាន sequence ផ្ទាល់ខ្លួន (មានគម្លាតនៅខាងមុខ)Music, voiceovers, sfx and tts each get their own sequence (with a leading gap).
  5. Layer ជា sequence វីដេអូ ដែលអាចមាន LayerShader (ជ្រុងមូល mask chroma key blend) ហើយ VideoCompositorSettings កំណត់ទីតាំង ទំហំ បង្វិល និងអាល់ហ្វាLayers are video sequences with a LayerShader (rounded corners, mask, chroma key, blend) and VideoCompositorSettings that set position, scale, rotation and alpha.
  6. នៅកម្រិត composition៖ OverlayEffect បង្កប់អត្ថបទ (export ប៉ុណ្ណោះ) ហើយ FrameDropEffect ពេល fps ក្រោម 30At composition level: an OverlayEffect burns in the text (export only), and a FrameDropEffect is added when fps is below 30.

GLSL shaderGLSL shaders

កូដ shader របស់ Android ជា GLSL ES 1.00 (texture2D, gl_FragColor, varying) ដែលភ្ជាប់ទៅ GlEffect របស់ Media3 តាមរយៈ GlslEffect ដែលជា wrapper ទូទៅមួយ។ shader ទទួលបាន uTexSampler (frame ចូល) ព្រមទាំង uSrcSize, uOutSize, uTime និងអ្វីៗដែល callback កំណត់ក្នុងមួយ frame។ outSize អនុញ្ញាតឱ្យ shader ប្តូរទំហំ frame ដែល ClipShader ប្រើដើម្បី render ជាទំហំ canvas ពេញ។

Android's shader code is GLSL ES 1.00 (texture2D, gl_FragColor, varying) plugged into Media3's GlEffect through GlslEffect, one general-purpose wrapper. A shader gets uTexSampler (the input frame) plus uSrcSize, uOutSize, uTime and whatever a per-frame callback sets. outSize lets a shader change the frame size, which ClipShader uses to render at full canvas size.

filter ទាំងអស់ដំណើរការក្នុង fragment shader តែមួយ (ClipShader) ដែលជ្រើស filter តាម uniform uFilter (0..9)។ ខាងក្រោមជាផ្នែក VHS៖ vhsColor ធ្វើ chromatic aberration ជាមួយរលក tracking ហើយសាខា filter ចុងក្រោយបន្ថែម scanline និង grain។ Vignette គឺសាខា k < 8.5 ដែលប្រើ smoothstep(0.85, 0.25, length(pp))។ សូមចំណាំថា Shaders.kt (ShaderEffect.VIGNETTE / VHS) នៅតែមានក្នុង source ប៉ុន្តែគ្មានអ្វីហៅវាទៀតទេ ព្រោះ ClipShader ជំនួសវា។

All the filters run in a single fragment shader (ClipShader) that picks the filter with a uFilter uniform (0..9). Below is the VHS part: vhsColor does a chromatic aberration with a wobble, and the last filter branch adds scanlines and grain. The vignette is the k < 8.5 branch, using smoothstep(0.85, 0.25, length(pp)). Note that Shaders.kt (ShaderEffect.VIGNETTE / VHS) still exists in the source but nothing calls it any more, since ClipShader superseded it.

Transition៖ T segment ដែល render ជាមុនTransitions: pre-rendered T segments

Media3 ចាត់ទុក sequence នីមួយៗជាអង្គភាពឯករាជ្យ ដូច្នេះ overlap នៃ clip ពីរក្នុងពេលតែមួយត្រូវការ composition តូចមួយផ្ទាល់ខ្លួន។ TransitionRenderer សាងសង់ composition ពីរ input (B នៅលើ A) ដោយមាន shader មួយសម្រាប់ម្ខាងៗ ហើយ export វាទៅ cacheDir/trans/T_<hash>.mp4។ key គឺ hash SHA-1 (កាត់ខ្លី) នៃ clip ទាំងពីរ ទំហំ ផ្ទៃខាងក្រោយ និងហត្ថលេខាឯកសារ (ឈ្មោះ:ទំហំ:ម៉ោងកែ)។ បន្ទាប់មកវាសម្អាត T file ចាស់ៗ ដោយរក្សា 40 ថ្មីបំផុត។ ក្នុង shader ទាំងនោះ slide និង push ត្រូវបានធ្វើដោយ overlay settings របស់ compositor (ទីតាំង) ឯអ្វីផ្សេងទៀតធ្វើដោយ shader ដែលសរសេរទាំងពណ៌ និងអាល់ហ្វា (អាល់ហ្វារបស់ B ធ្វើឱ្យ wipe ក្លាយជា wipe ពិតប្រាកដ)។

Media3 treats each sequence as an independent stage, so an overlap of two clips at the same moment needs a small composition of its own. TransitionRenderer builds a two-input composition (B on top of A) with one shader per side and exports it to cacheDir/trans/T_<hash>.mp4. The key is a truncated SHA-1 hash over both clips, the size, the background and file signatures (name:size:modified time). Afterwards it prunes old T files, keeping the newest 40. Among those shaders, slides and pushes are done with the compositor's overlay settings (position), and everything else with a shader that writes colour plus alpha (B's alpha is what makes a wipe a real wipe).

ឥទ្ធិពលដែលអ្នកប្រើអាចសង្កេតឃើញ៖ ពេលអ្នកប្តូរ transition preview បង្ហាញការកាត់ស្រួតត្រង់ទីតាំងដដែល រហូតដល់ T segment ត្រូវបាន render រួច ហើយបន្ទាប់មកប្តូរទៅ transition ពិតដោយស្វ័យប្រវត្តិ។ ស្ថានភាពនេះត្រូវបានបង្ហាញដោយ PreviewController.renderingTransitions ជាមួយ progress ហើយចំណុចកាត់ដែលនៅជិត playhead បំផុតត្រូវបាន render មុន។ ពេល export ជំហាននេះប្រើ 20% ដំបូងនៃ progress។

A user-visible consequence: when you change a transition the preview shows a hard cut at the same position until the T segment has been rendered, then swaps in the real transition automatically. That state is exposed as PreviewController.renderingTransitions with progress, and the cut nearest the playhead renders first. On export this step accounts for the first 20% of the progress bar.

Effects, layers, overlayEffects, layers and overlays

Effects។ ទាំង 16 ប្រភេទជាសាខានៃ fragment shader តែមួយ FxEffects ដែលជ្រើសដោយ uKind។ Effect ដែលត្រួតគ្នាក្នុងពេលវេលាត្រូវបានដាក់ទៅ "lane" ផ្សេងគ្នា (មួយ pass ក្នុងមួយ lane) ដោយក្បួន interval-scheduling ខ្លី។ Layers។ sequence របស់ layer ត្រូវបានរៀបតាមលំដាប់ដូចដែល compositor របស់ Media3 គូរ input 0 ចុងក្រោយ (នៅលើបំផុត) ដូច្នេះ layer លើបំផុតគឺ input 0 ហើយ track មេជា input ខ្ពស់បំផុត។ ដើម្បីឱ្យ sequence ដែលចាប់ផ្តើមក្រោយអាចត្រូវបាន composite កូដបំពេញគម្លាតដោយបំណែក mute នៃវីដេអូ layer ខ្លួនឯង ហើយ LayerCompositorSettings លាក់វាដោយ alpha 0 នៅខាងក្រៅ [startMs, endMs)។ Overlay អត្ថបទ។ ProjectOverlay ជា BitmapOverlay មួយគូររាល់ overlay សកម្មលើ bitmap ទំហំ frame ដោយប្រើ TextRenderer ដូចគ្នានឹង preview ហើយ re-render តែនៅពេលរូបអាចផ្លាស់ប្តូរ (ជំនួសគ្នារវាង bitmap ពីរ)។

Effects. All 16 kinds are branches of one fragment shader, FxEffects, selected by uKind. Effects that overlap in time are assigned to separate "lanes" (one pass per lane) by a short interval-scheduling rule. Layers. Layer sequences are ordered to suit Media3's compositor, which paints input 0 last (on top): the top layer is input 0 and the main track is the highest input. So that a sequence that starts late can still be composited, the code pads the gap with muted pieces of the layer's own video, and LayerCompositorSettings hides them with alpha 0 outside [startMs, endMs). Text overlay. ProjectOverlay is a BitmapOverlay that draws every active overlay onto a frame-sized bitmap with the same TextRenderer the preview uses, and only re-renders when the picture can change (alternating between two bitmaps).

អត្ថបទ និង emoji sticker ជា overlay ប្រភេទ text ឬ sticker។ គោលការណ៍សំខាន់គឺ renderer តែមួយ៖ លើ iOS OverlayRenderer គូរ overlay ទៅជា CGImage ហើយ SwiftUI (preview) និង Core Image (export) ប្រើរូបនោះដូចគ្នា។ លើ Android TextRenderer គូរលើ Canvas ទាំង Compose (preview) និង BitmapOverlay (export)។ គ្រប់ទំហំទាំងអស់ជាប្រភាគនៃ canvas ដូច្នេះលទ្ធផលត្រូវគ្នាទោះ resolution ណាក៏ដោយ។

Text and emoji stickers are overlays of kind text or sticker. ការ shaping ភាសាខ្មែរKhmer shaping

អក្សរខ្មែរមិនមែនជាតួអក្សរដាច់ដោយឡែកទេ។ ព្យញ្ជនៈ + ជើង (coeng + ព្យញ្ជនៈរង) + ស្រៈ បង្កើតជា grapheme cluster មួយ ហើយ glyph ចុងក្រោយត្រូវបាន shape តាមក្បួនរបស់ font ដែលជួនកាលខ្ពស់ជាង ឬទាបជាងបន្ទាត់ធម្មតា។ កូដបានដោះស្រាយបញ្ហាទាំងនេះដូចខាងក្រោម (ពិតនៅក្នុង source)៖

Khmer text is not a row of independent characters. A consonant plus a subscript (coeng + subscript consonant) plus vowels forms a single grapheme cluster, and the final glyphs are shaped by the font's rules and are sometimes taller or lower than a normal line. What the code does about it (all of this is in the source):

  • iOS ប្រើ CoreText សម្រាប់ទាំង layout និង outline (CTFramesetter, CTRunGetGlyphs, CTFontCreatePathForGlyph) ដូច្នេះ cluster និង subscript ត្រូវតែត្រឹមត្រូវ។iOS uses CoreText for both layout and outlines (CTFramesetter, CTRunGetGlyphs, CTFontCreatePathForGlyph), so clusters and subscripts come out right.
  • Letter spacing ស្ថិតនៅចន្លោះ cluster តែប៉ុណ្ណោះ៖ kern ត្រូវបានដាក់លើ UTF-16 unit ចុងក្រោយនៃ cluster នីមួយៗ ដូច្នេះព្យញ្ជនៈ + coeng + ជើង + ស្រៈ មិនត្រូវបានទាញចេញពីគ្នាទេ។Letter spacing is applied only between clusters: the kern is attached to the last UTF-16 unit of each cluster, so consonant + coeng + subscript + vowels are never pulled apart.
  • Typewriter បង្ហាញ cluster ទាំងមូល៖ iOS រាប់ Character របស់ Swift (grapheme cluster) ហើយ Android ប្រើ BreakIterator.getCharacterInstance() ដូច្នេះជើង និងស្រៈមិនលេចមកមុនព្យញ្ជនៈរបស់វាទេ។The typewriter reveals whole clusters: iOS counts Swift Characters (grapheme clusters) and Android uses BreakIterator.getCharacterInstance(), so a subscript or vowel never appears before its consonant.
  • gradient តាមកម្ពស់ ink ពិត៖ លើ iOS gradient លាតពី ink bounds ទាំងមូល (រួមទាំងជង់ខ្មែរ) ហួសគែមទាំងសងខាង ដើម្បីកុំឱ្យមានផ្នែកណាលើស ឬក្រោមប្រអប់បន្ទាត់ដែលមិនបានគូរ។The gradient follows the real ink height: on iOS it spans the glyphs' full ink bounds (Khmer stacks included), extended past both ends so nothing above or below the line box is left undrawn.
  • Caption និង TTS ស្គាល់ខ្មែរ៖ ពេលបំបែក caption ជាឃ្លា ។ (ខណ្ឌ) ត្រូវបានចាត់ទុកជាចុងប្រយោគលើ iOS ហើយ TTS ជ្រើស km-KH ដោយស្វ័យប្រវត្តិ ពេលអត្ថបទមានតួអក្សរក្នុងជួរ U+1780–U+17FF។ ប្រសិនបើឧបករណ៍គ្មានសំឡេងខ្មែរ កម្មវិធីបង្ហាញ "No Khmer voice on this device"។Captions and TTS know Khmer: when captions are split into phrases the Khmer full stop ។ counts as a sentence end on iOS, and TTS picks km-KH automatically when the text contains characters in U+1780–U+17FF. If the device has no Khmer voice the app says "No Khmer voice on this device".

ដែនកំណត់ដែលស្គាល់៖ លើ Android ចន្លោះអក្សរប្រើ TextPaint.letterSpacing ហើយ shaping ត្រូវបានទុកឱ្យជង់អត្ថបទរបស់ប្រព័ន្ធ។ គ្មានផ្លូវកូដពិសេសសម្រាប់ខ្មែរលើ Android ក្រៅពី BreakIterator សម្រាប់ typewriter ទេ។ ដូច្នេះរូបរាងអក្សរខ្មែរលើ Android អាស្រ័យលើប្រព័ន្ធ និង font។ យើងមិនមានការវាស់វែងប្រៀបធៀបណាមួយដើម្បីផ្សព្វផ្សាយទេ។

A known limit: on Android letter spacing uses TextPaint.letterSpacing and shaping is left to the platform text stack. There is no Khmer-specific code path on Android beyond BreakIterator for the typewriter, so Khmer rendering on Android depends on the platform and the font. We have no measurement to publish comparing the two.

មុខងារនេះរកមនុស្សក្នុងមួយ frame ៗ ហើយ render clip ថ្មីមួយ ទៅឯកសារ ដែលមនុស្សស្ថិតនៅលើពណ៌រាបស្មើ ឬផ្ទៃខាងក្រោយ blur។ ឯកសារនោះរស់នៅក្នុង media/ ហើយ clip ចង្អុលទៅវាតាម cutoutFileName (អ្វីដែលកម្មវិធីលេងនៅពេលនោះគឺ cutoutFileName ?? fileName) ជាមួយ cutoutBackground កត់ត្រាជម្រើស (ពណ៌ hex ឬ "blur")។ ការលុបចោលគឺគ្រាន់តែសម្អាតតម្លៃ cutoutFileName ហើយលុបឯកសារ។ ការដំណើរការធ្វើលើ clip ប្រភពទាំងមូល ហើយ trim/speed អនុវត្តបន្ទាប់។

The feature finds the person in each frame and renders a new clip to a file in which the person sits over a flat colour or a blurred background. That file lives in media/, and the clip points to it through cutoutFileName (what the engine plays is then cutoutFileName ?? fileName) with cutoutBackground recording the choice (a hex colour or "blur"). Restoring the original just clears cutoutFileName and deletes the file. The work is done on the whole source clip; trims and speed apply afterwards.

One important detail: the app counts how many frames Vision segmented successfully. If it is zero, it aborts and reports "person segmentation unavailable on this device" instead of silently writing the untouched clip. The README says it runs at about real time on recent iPhones, and it can be cancelled.

Android៖ ML Kit Selfie SegmentationAndroid: ML Kit Selfie Segmentation

Android ត្រូវបានសាងសង់ខុសគ្នា។ គ្មាន loop អាន/សរសេរ frame ដោយដៃទេ។ វាប្រើ Transformer ជាមួយ effect បី៖ Presentation បន្ថយទៅចំហៀងខ្លី ≤ 720 (ទំហំជាលេខគូ) បន្ទាប់មកជំហានមួយដែលជំនួស frame មូលដ្ឋានទាំងមូល (RgbMatrix ដែលជំនួសគ្រប់ពណ៌ដោយពណ៌រាបស្មើ ឬ GaussianBlur(25f) សម្រាប់ blur) ហើយចុងក្រោយ OverlayEffect ដែលគូរមនុស្សត្រឡប់មកពីលើវិញ។ CutoutOverlay.getBitmap(presentationTimeUs) ទាញ frame ប្រភពមួយនៅ timestamp នោះដោយ MediaMetadataRetriever.getScaledFrameAtTime(..., 512, 512) ឱ្យ ML Kit (STREAM_MODE) segment ហើយប្រើតម្លៃ float របស់ mask ជា alpha ដោយផ្ទាល់។ ឯកសារលទ្ធផលជា cutout_<millis>.mp4 ហើយសំឡេងដើមត្រូវបាន Transformer ដឹកតាមធម្មតា។

Android is built differently. There is no hand-written read/write frame loop. It uses a Transformer with three effects: Presentation scales down to a short side of at most 720 (even dimensions), then a step that wipes the whole base frame (an RgbMatrix that replaces every colour with the flat colour, or GaussianBlur(25f) for blur), and finally an OverlayEffect that draws the person back on top. CutoutOverlay.getBitmap(presentationTimeUs) pulls one source frame at that timestamp with MediaMetadataRetriever.getScaledFrameAtTime(..., 512, 512), lets ML Kit (STREAM_MODE) segment it, and uses the float mask values directly as alpha. The output is cutout_<millis>.mp4, and the original audio is carried by the Transformer as usual.

Mask refinement។ មិនមានជំហានកែ mask បន្ថែមលើ platform ណាមួយទេ។ ទាំង Vision និង ML Kit ផ្តល់ mask ទន់ (soft) ហើយកូដប្រើវាដោយផ្ទាល់ជា alpha ឬ mask (បន្ទាប់ពីពង្រីកទំហំ) ដូច្នេះគុណភាពគែមរបស់ cutout គឺជាគុណភាពរបស់ model។

Mask refinement. There is no extra mask-refinement step on either platform. Vision and ML Kit both return a soft mask, and the code uses it directly as alpha or mask (after scaling), so the cutout's edge quality is the model's quality.

ការដោះដូរ៖ លើ Android តួមនុស្សត្រូវបានយកពី frame ដែលស្នើក្នុងដែនកំណត់ 512×512 រួចគូរពង្រីកលើ output ដែលមានចំហៀងខ្លីរហូតដល់ 720 ដូច្នេះតួមនុស្សអាចមើលទៅទន់ជាងផ្ទៃខាងក្រោយ។ លើ iOS segmentation ដំណើរការលើ frame ទំហំដើម។ Android ត្រូវបានសាងសង់បែបនេះដើម្បីល្បឿន (comment ក្នុងកូដ៖ "segmentation + per-frame bitmap upload is the bottleneck")។

Trade-off: on Android the person comes from a frame requested within 512×512 bounds and is drawn scaled up over an output of up to 720 short side, so the person can look softer than the background. On iOS segmentation runs on the full-size frame. Android is built this way for speed (the code comment: "segmentation + per-frame bitmap upload is the bottleneck").

កម្រិតសំឡេងដើមOriginal audio volume

កម្រិតសំឡេងចុងក្រោយរបស់ clip គឺ clip.volume × project.originalAudioVolume លើទាំងពីរកម្មវិធី។ លើ iOS ប្រសិនបើតម្លៃនេះតូចជាង 0.001 សំឡេងរបស់ clip មិនត្រូវបានបញ្ចូលក្នុង composition ទាល់តែសោះ។ ភ្លេងចាប់ផ្តើមនៅ startMs ជាមួយ trimStartMs ហើយប្រវែងត្រូវបានកាត់ដើម្បីកុំឱ្យហួសចុង timeline។ លំនាំដើម volume ភ្លេងគឺ 1.0 លើ iOS ហើយ 0.6 លើ Android (importMusic)។

ថតសំឡេងរៀបរាប់ (voiceover)Recording a voiceover

iOS uses an AVAudioEngine with a tap on the input node writing straight into an AVAudioFile as AAC .m4a (128 kbps). Both start at the playhead and end up as an audio item of kind voiceover in media/. A recording shorter than 200 ms is rejected on iOS as "Recording too short".

Fade និង crossfade។ iOS សរសេរ envelope ចូល AVMutableAudioMix ជា volume ramp រវាងចំណុចបំបែក (breakpoint) រួមទាំង crossfade ប្រភេទ equal-power ដែលយកសំណាក 9 ចំណុច។ Android គណនា gain សម្រាប់ sample នីមួយៗក្នុង GainEnvelopeProcessor ហើយ crossfade របស់ transition ប្រើគូ sin/cos ដូចគ្នានៅក្នុង T segment។

Fades and crossfades. iOS writes the envelope into an AVMutableAudioMix as volume ramps between breakpoints, including an equal-power crossfade sampled at 9 points. Android computes gain per sample in a GainEnvelopeProcessor, and the transition crossfade uses the same sin/cos pair inside the T segment.

Voice effect។ មានប្រាំ៖ chipmunk (+7 semitone), deep (−5), robot, echo, radio (band-pass)។ iOS render ជាមុន offline ជាមួយ AVAudioEngine (manual rendering mode) ដោយ AVAudioUnitTimePitch (+700/−500 cent), AVAudioUnitDelay, AVAudioUnitDistortion និង AVAudioUnitEQ ទៅជាឯកសារ cache fx_<id>_<effect>.m4a។ Android ដំណើរការវាតាមពេលវេលាពិតក្នុងច្រវាក់ audio processor របស់ Transformer៖ SonicAudioProcessor សម្រាប់ pitch, ឯ robot (ring modulation 48 Hz), echo (feedback delay) និង radio (biquad high-pass 400 Hz + low-pass 3400 Hz + tanh) គឺជា VoiceFxProcessor ផ្ទាល់ខ្លួន។

Voice effects. There are five: chipmunk (+7 semitones), deep (−5), robot, echo, radio (band-pass). iOS pre-renders offline with AVAudioEngine in manual rendering mode, using AVAudioUnitTimePitch (+700 / −500 cents), AVAudioUnitDelay, AVAudioUnitDistortion and AVAudioUnitEQ, into a cached file fx_<id>_<effect>.m4a. Android runs them in real time in the Transformer's audio-processor chain: SonicAudioProcessor for pitch, and a custom VoiceFxProcessor for robot (48 Hz ring modulation), echo (feedback delay) and radio (high-pass 400 Hz and low-pass 3400 Hz biquads plus tanh).

Sound effects និង TTS។ កញ្ចប់ sfx ចំនួន 20 ត្រូវបានបង្កប់ជា .m4a ដែល spec ថាបង្កើតដោយ procedural និងឥតបង់ថ្លៃសិទ្ធិ (royalty-free)។ Text-to-speech ប្រើ AVSpeechSynthesizer.write (iOS) និង TextToSpeech.synthesizeToFile (Android) ជាមួយសំឡេងលើឧបករណ៍ប៉ុណ្ណោះ ហើយបន្ថែមជា audio item ប្រភេទ tts។ ប្រភេទ audio ទាំងប្រាំគឺ music, voiceover, extracted, sfx និង tts។

Sound effects and TTS. A pack of 20 sound effects is bundled as .m4a, which the spec says were generated procedurally and are royalty-free. Text-to-speech uses AVSpeechSynthesizer.write (iOS) and TextToSpeech.synthesizeToFile (Android) with on-device voices only, and adds an audio item of kind tts. The five audio kinds are music, voiceover, extracted, sfx and tts.

ការលាយពេល exportMixing at export

លើ iOS សំឡេងទាំងអស់ (clip A/B, ភ្លេង, សំឡេងរៀបរាប់, សំឡេងរបស់ layer) ជា track នៅក្នុង composition ដែលមាន AVAudioMix។ ពេល export AVAssetReaderAudioMixOutput អានវាជា PCM 16-bit 44.1 kHz ស្តេរីអូ ហើយ writer អ៊ិនកូដជា AAC (128 kbps, ឬ 192 kbps ពេល quality ជា High)។ លើ Android audio item នីមួយៗជា sequence ផ្ទាល់ខ្លួនក្នុង composition ដែល Transformer លាយ ហើយ stereoOut() (ChannelMixingAudioProcessor) ធានាថា mono និង stereo ទាំងពីរចេញជា stereo។

On iOS all the audio (main clips A/B, music, voiceovers, layer audio) are tracks of one composition with an AVAudioMix. At export an AVAssetReaderAudioMixOutput reads it as 16-bit 44.1 kHz stereo PCM and the writer encodes AAC (128 kbps, or 192 kbps at High quality). On Android every audio item is its own sequence in the composition, which the Transformer mixes, and stereoOut() (a ChannelMixingAudioProcessor) guarantees that mono and stereo inputs both come out as stereo.

Export៖ encoder, progress និងការរក្សាទុកExport: encoder settings, progress and saving #

ជម្រើស export មានបួន ហើយត្រូវបានចងចាំក្នុង UserDefaults / SharedPreferences៖ ដំណោះស្រាយ (720p, 1080p, 2K = 1440, 4K = 2160 ជាចំហៀងខ្លី), frame rate (24, 30, 60), គុណភាព (Low / Recommended / High) និង codec (H.264 ឬ HEVC)។ ទំហំ output ជាលេខគូជានិច្ច សម្រាប់ encoder។ អ្នកប្រើឃើញទំហំឯកសារប៉ាន់ស្មានមុនពេល export។

Export has four options, remembered in UserDefaults / SharedPreferences: resolution (720p, 1080p, 2K = 1440, 4K = 2160, as the short side), frame rate (24, 30, 60), quality (Low / Recommended / High) and codec (H.264 or HEVC). Output dimensions are always even for the encoder. The user sees an estimated file size before exporting.

BitrateBitrate

គុណភាពកំណត់ bits per pixel per frame៖ Low 0.07, Recommended 0.12, High 0.2។ Bitrate វីដេអូ = ទទឹង × កម្ពស់ × fps × bpp (យ៉ាងតិច 500 kbps)។ ឧទាហរណ៍គណនាពីរូបមន្ត (មិនមែនការវាស់)៖ 1080×1920 ជា 30 fps ក្នុង Recommended = 2,073,600 × 30 × 0.12 ≈ 7.46 Mbps។ iOS គុណ 0.6 ពេល HEVC (កូដមាន comment ថា "HEVC reaches the same quality with about 60% of the H.264 bits") ហើយ Android រក្សាគោលដៅ bpp ដដែល រួចទុកឱ្យ encoder ប្រើតិចជាង (ការប៉ាន់ស្មានទំហំរបស់វាគុណ 0.8)។

Quality sets the bits per pixel per frame: Low 0.07, Recommended 0.12, High 0.2. Video bitrate = width × height × fps × bpp (at least 500 kbps). A worked example from the formula (not a measurement): 1080×1920 at 30 fps, Recommended = 2,073,600 × 30 × 0.12 ≈ 7.46 Mbps. iOS multiplies by 0.6 for HEVC (the code comment: "HEVC reaches the same quality with about 60% of the H.264 bits"); Android keeps the same bpp target and lets the encoder undershoot (its size estimate uses a 0.8 factor).

លំហូរ progress និងការបោះបង់Progress and cancellation

iOS។ Exporter បង្កើត composition (includeOverlays: true) ហើយអាន frame ដែលបាន render ពី AVAssetReaderVideoCompositionOutput ទៅ AVAssetWriter ដោយ requestMediaDataWhenReady។ Progress គឺ timestamp នៃ frame ចុងក្រោយ ÷ ប្រវែងសរុប កំណត់ត្រឹម 0.99 រហូតដល់បញ្ចប់ពិតប្រាកដ។ ការបោះបង់កំណត់ CancelFlag ដែល loop ពិនិត្យរាល់ frame ហើយបន្ទាប់មកបិទ reader/writer និងលុបឯកសារដែលសរសេរមិនទាន់ចប់។ Android។ ExportPipeline render T segment (0–20% នៃ progress) បន្ទាប់មកបង្កើត composition និងរត់ Transformer។ progress ត្រូវបាន poll រាល់ 200 ms ហើយការបោះបង់ coroutine ហៅ transformer.cancel()។ មុន export Android កំណត់ codec និង resolution ទៅអ្វីដែល encoder របស់ឧបករណ៍គាំទ្រ (MediaCodecList) ហើយកត់ត្រាសារ ឧ. "limited to 1080p by this device"។

iOS. Exporter builds the composition (includeOverlays: true) and pulls rendered frames from an AVAssetReaderVideoCompositionOutput into an AVAssetWriter with requestMediaDataWhenReady. Progress is the last frame's timestamp divided by the total length, capped at 0.99 until genuinely finished. Cancelling sets a CancelFlag that the loop checks on every frame, then the reader and writer are shut down and the half-written file is deleted. Android. ExportPipeline renders the T segments (0–20% of progress), then builds the composition and runs the Transformer. Progress is polled every 200 ms and cancelling the coroutine calls transformer.cancel(). Before exporting, Android clamps codec and resolution to what the device's encoders support (MediaCodecList) and reports a note, for example "limited to 1080p by this device".

HEVC ត្រូវបានផ្តល់ជូនតែនៅពេលឧបករណ៍គាំទ្រ (iOS៖ មាន export preset HEVC ក្នុងបញ្ជី; Android៖ មាន encoder video/hevc)។ បើមិនដូច្នេះទេ វាធ្លាក់ត្រឡប់ទៅ H.264។ ជម្រើស 60 fps ត្រូវបានប្រើក្នុងការគណនា bitrate និងកំណត់ frameDuration របស់ composition លើ iOS; លើ Android កូដបន្ថែម FrameDropEffect តែពេល fps ក្រោម 30 ប៉ុណ្ណោះ។

HEVC is offered only when the device supports it (iOS: an HEVC export preset is listed; Android: a video/hevc encoder exists), otherwise it falls back to H.264. The frame-rate choice feeds the bitrate formula and sets the composition's frameDuration on iOS; on Android the code adds a FrameDropEffect only when fps is below 30.

រក្សាទុកទៅ Photos / MediaStoreSaving to Photos or MediaStore

iOS ស្នើការអនុញ្ញាតតែ បន្ថែម (.addOnly) ហើយបង្កើត PHAssetCreationRequest។ ឯកសារមានឈ្មោះ KamKut_<ឈ្មោះ>_<yyyyMMdd_HHmmss>.mp4។ បន្ទាប់ពី export រួចអ្នកអាច Share ផងដែរ (ShareLink) ដើម្បីរក្សាទុកក្នុង Files ជាដើម។ Android ចម្លងទៅ Movies/KamKut ក្នុង MediaStore ដោយប្រើ IS_PENDING ដើម្បីកុំឱ្យ app ផ្សេងឃើញឯកសារមិនទាន់ចប់ ហើយលើ API 28 (មុន scoped storage) វាចម្លងត្រង់ទៅថត Movies/KamKut រួចស្កេនដោយ MediaScannerConnection។

iOS asks for add-only permission (.addOnly) and creates a PHAssetCreationRequest. Files are named KamKut_<name>_<yyyyMMdd_HHmmss>.mp4. After exporting you can also Share (ShareLink), for example to save into Files. Android copies into Movies/KamKut in MediaStore using IS_PENDING so other apps never see a half-written file, and on API 28 (before scoped storage) it copies straight into the Movies/KamKut folder and scans it with MediaScannerConnection.

របៀបដែលវាត្រូវបានផ្ទៀងផ្ទាត់How it is verified

repository នេះមិនមានសំណុំ unit test ស្វ័យប្រវត្តិទេ។ ជំនួសវិញ កម្មវិធីទាំងពីរមាន harness សម្រាប់ debug ដែលរត់ pipeline ពិតប្រាកដ។ លើ iOS DebugHooks.swift (មានតែក្នុង build DEBUG ប៉ុណ្ណោះ គ្មានក្នុង release) ទទួល launch argument ដូចជា -kamkutExportTest, -kamkutFrames (render PNG តាម compositor ដូចគ្នា), -kamkutCaptionTest, -kamkutTtsTest, -kamkutActions (សកម្មភាព EditorModel ជាស្គ្រីប) និង -kamkutLocales ហើយចេញលទ្ធផលទៅ kk_debug.log។ លើ Android មាន DebugExportActivity និង DebugPreviewActivity (នៅក្នុង source set debug ប៉ុណ្ណោះ) ដែល export គម្រោងដោយគ្មាន UI និងថតរូបអេក្រង់ preview ពិតដោយ PixelCopy តាម adb។ នេះមានន័យថា គុណភាពផ្អែកលើការផ្ទៀងផ្ទាត់ដោយដៃ និងស្គ្រីប ជាជាងការធ្វើតេស្តស្វ័យប្រវត្តិ។ យើងនិយាយដោយត្រង់ពីរឿងនេះ។

The repository has no automated unit-test suite. Instead, both apps carry debug harnesses that run the real pipeline. On iOS, DebugHooks.swift (compiled only in DEBUG, never in release) reads launch arguments such as -kamkutExportTest, -kamkutFrames (renders PNGs through the same compositor), -kamkutCaptionTest, -kamkutTtsTest, -kamkutActions (scripted EditorModel actions) and -kamkutLocales, and writes to kk_debug.log. On Android there are DebugExportActivity and DebugPreviewActivity (in the debug source set only) that export a project headlessly and screenshot the real preview with PixelCopy over adb. In other words, quality rests on manual and scripted verification rather than automated tests, and we would rather say so plainly.

ដែនកំណត់ និងការដោះដូរLimits and trade-offs

  • Simulator មិនអាចធ្វើ Vision segmentation បាន។ ការកាត់ផ្ទៃខាងក្រោយត្រូវតែសាកល្បងលើឧបករណ៍ពិត (ឬ macOS)។ កូដបង្ខំ CPU លើ Simulator ហើយបរាជ័យយ៉ាងច្បាស់ លុះត្រាតែគ្មាន frame ណាមួយបាន segment។ Simulator ក៏មិនមាន camera roll វីដេអូលំនាំដើមដែរ (អូសឯកសារវីដេអូទៅលើបង្អួច Simulator)។The Simulator cannot run Vision segmentation. Background removal has to be tested on a real device (or macOS). The code forces the CPU on the Simulator and fails loudly unless at least one frame was segmented. The Simulator also has no camera-roll videos by default (drag a video file onto the Simulator window).
  • Metal kernel មិនដំណើរការលើ Simulator។ Vignette និង VHS ប្រើច្រវាក់ Core Image ដែលស្មើគ្នាជំនួស ដូច្នេះរូបរាងស្រដៀងគ្នា ប៉ុន្តែមិនដូចគ្នាទាំងស្រុងទេ។Metal kernels do not run on the Simulator. Vignette and VHS use equivalent Core Image chains there, so the look is similar but not identical.
  • "ដូចគ្នា" មានន័យថាស្របតាម spec មិនមែនដូចគ្នាតាម pixel ទេ។ Filter ពណ៌ត្រូវបានសរសេរដាច់ដោយឡែក (Core Image photo effect លើ iOS ធៀបនឹងគណិតវិទ្យា matrix ក្នុង GLSL លើ Android) ចលនា loop និង gradient មានប៉ារ៉ាម៉ែត្រខុសគ្នា preview ប្រើ resolution ទាបជាង export (720 លើ iOS, 540 លើ Android)។"Identical" means identical to the spec, not pixel for pixel. Colour filters are written separately (Core Image photo effects on iOS, matrix math in GLSL on Android), loop animations and the gradient style have different parameters, and the preview renders at a lower resolution than the export (720 on iOS, 540 on Android).
  • Blend mode លើ Android ជាការប៉ាន់ស្មាន។ compositor របស់ Media3 គ្រាន់តែលាយ alpha ដូច្នេះ multiply/darken ត្រូវបាន map ទៅ "ខ្មៅដែលមាន alpha = 1 − luminance" ហើយ screen/lighten/add ទៅ "alpha = ភាពភ្លឺ"។ កូដនិយាយថាវាត្រឹមត្រូវសម្រាប់ footage ងងឹត ឬភ្លឺ ហើយប៉ាន់ស្មានក្នុងករណីផ្សេង។ iOS ប្រើ blend filter ពិតរបស់ Core Image។Blend modes on Android are approximations. Media3's compositor only alpha-blends, so multiply/darken are mapped to "black with alpha = 1 − luminance" and screen/lighten/add to "alpha = brightness". The code says this is exact for dark- or light-backed footage and approximate otherwise. iOS uses real Core Image blend filters.
  • Transition លើ Android ត្រូវការ render ជាមុន។ ពេលអ្នកប្តូរ transition នឹងមានរយៈពេលខ្លីដែល preview បង្ហាញការកាត់ស្រួត។ លើ iOS transition ជាពេលវេលាពិត។Transitions on Android need a pre-render. After you change a transition there is a short window in which the preview shows a hard cut. On iOS transitions are real-time.
  • Cutout លើ Android មានគុណភាពទាបជាង ដូចដែលបានពន្យល់ខាងលើ (frame សម្រាប់ segmentation ≤ 512 ហើយការ render ចំហៀងខ្លី ≤ 720)។ ដំណើរការរបស់ iOS ប្រហែលពេលវេលាពិតលើ iPhone ថ្មីៗ (ទៅតាម README)។Cutout on Android is lower fidelity, as explained above (segmentation frame within 512, working short side at most 720). iOS processing takes about real time on recent iPhones, according to the README.
  • Captions ត្រូវការ recogniser លើឧបករណ៍។ iOS ប្រើ requiresOnDeviceRecognition ហើយ Android ត្រូវការ API 33+ និង isOnDeviceRecognitionAvailable (SPEC សរសេរ API 31+ ប៉ុន្តែកូដតម្រូវ 33)។ ខ្មែរត្រូវបានបង្ហាញជាជម្រើសបិទ ពេលឧបករណ៍មិនមាន ហើយកម្មវិធីមិនធ្លាក់ទៅប្រើបណ្តាញជាដាច់ខាត។Captions need an on-device recogniser. iOS uses requiresOnDeviceRecognition; Android needs API 33+ and isOnDeviceRecognitionAvailable (the spec says API 31+, the code requires 33). Khmer is shown as a disabled option when the device lacks it, and the app never falls back to the network.
  • HEVC និង 4K អាស្រ័យលើឧបករណ៍។ Android កាត់ resolution និង codec ទៅអ្វីដែល encoder គាំទ្រ ហើយ iOS បង្ហាញ HEVC តែនៅពេលមាន preset។HEVC and 4K depend on the device. Android clamps resolution and codec to what its encoders support, and iOS offers HEVC only when a preset exists.
  • Reverse ត្រូវ render ជាមុនម្តង។ ទាំងពីរបង្កើតច្បាប់ចម្លងបញ្ច្រាស (rev_*.mp4) ហើយ cache។ iOS អាន frame ថយក្រោយជាចំណែកតូចៗដើម្បីកំណត់ memory ហើយ Android អ៊ិនកូដ H.264 all-intra រួចរៀបបញ្ច្រាសដោយមិនចាំបាច់ decode ម្តងទៀត។Reverse needs a one-time pre-render. Both build a reversed copy (rev_*.mp4) and cache it. iOS reads frames backwards in small chunks to bound memory; Android encodes an all-intra H.264 stream and then muxes it in reverse, with no second decode.
